# Product acceptance matrix

This matrix tracks required proof, not implementation completion. `qualify.py`
reports the exact automated checks actually executed. Every unchecked layer
remains a release gap even if unit tests or connectivity probes pass.

| Plan scenario | Required evidence | Executable local coverage | Remaining integrated / real gate |
| --- | --- | --- | --- |
| 1. Existing Multica work | Canonical Multica issue, linked implementation/review runs and GitHub artifact, one commitment in web + remote CLI | `authority` separates source tuples | Import an existing linked issue through the real reader; compare canonical IDs across views and a second machine |
| 2. GitHub authority | Existing independently GitHub-owned work, source links, no Multica migration | `authority` rejects direct local external mutation | Real GitHub reader + web/CLI; use an issue rather than confusing a PR-only list result with issue ownership |
| 3. Approved remote repo | Exact host, path, Git SHA, timestamps; failed access visibly stale | `outage` retains stale last-good observation | Real approved SSH reader success, controlled failure and recovery without changing the source |
| 4. Remote duplicate/out-of-order | One observation/event/action semantic identity, newer source state retained | `replay` duplicates, conflict, source sequence, crash | Remote CLI submission; assert event/action counts and clock-skew behavior |
| 5. Deployment investigator | Separate CI, artifact, deployment, traffic, and user-visible checks | `completion` rejects an empty completed-run claim | Actual bounded investigator against a real target; missing layers remain uncertain |
| 6. PM across channels | Real scrum conversation, same authorized project context, correct sender and origin | No real-channel claim | Web + dedicated Telegram + Discord conversations; transport receipt alone insufficient |
| 7. Failed decision delivery | Answer persists; failed/unknown visible; retry avoids confirmed mutation | PM package tests must run after integration | Controlled action executor failure, restart and read-back; real writes only on explicitly approved fixtures |
| 8. Run != acceptance | Run completion leaves unmet acceptance waiting/review/correction | `completion` | PM disposition and user-facing presentation with accepted artifact gate |
| 9. Restart pending work | Ownership, instructions, decisions, attempts, deduplication survive | `baseline`, `replay`, `outage` restart real core | Collector queue claim/recovery plus PM pending and ambiguous delivery restart |
| 10. Generated reader lifecycle | Immutable code revision, validation, real canary, activation, suspend/rollback | No synthetic lifecycle success claimed | Supported Linux runner; actual generation through configured agent; canary provenance cannot be self-asserted |
| 11. Least privilege | Runtime filesystem/network/credential/source-write denial within approved envelope | No host-runtime proof from static validation | Enforced isolation runner with harmless fixtures; unsupported platforms fail closed |
| 12. Views | Same work in table + board, inbox lifecycle independent, dates/dependencies retained | `views` checks API projection and read independence | Rendered browser/mobile/keyboard checks, actual inbox dismiss/snooze and filtered pagination |

| 14. Authorization | Cross-workspace and shared-channel users denied unauthorized reads/actions | `baseline`, `authority` independently bootstrapped tokens | Channel signatures + exact tuple mapping + per-principal permissions; no ambient human impersonation |

## Review questions by owning lane

- **Core/contracts:** Can canonical source identity be rewritten through an
  existing card route? Are external card move/resolve/patch routes also guarded?
  Do equal observation timestamps or mixed sequenced/unsequenced reports regress
  evidence? Is failed-refresh ordering independent of successful-source ordering?
  Does pagination remain stable under filters and concurrent source changes?
- **Observations:** Is target scope resolved from registered connection policy?
  Are redirects, page/output/time bounds and retry hints enforced? Does a saved
  refresh request have a runtime consumer? Does restart restore due times and
  prevent overlapping ownership? Is canary evidence generated by the runner
  rather than provided by the adapter author?
- **PM/channels:** Is approval bound to current work revision, actual human
  identity and permission scope? Can one principal access another's conversation
  by ID or replay key? Does request-key reuse with a changed body conflict? Does
  uncertain delivery reconcile without resend? Does a completed agent process
  remain pending until an authenticated PM response arrives?
- **UI:** Can an operator see source, freshness, next actor, decision and receipt
  together? Are unavailable provider, partial coverage, stale source and unknown
  delivery visible? Does a board interaction imply a source action that never
  happened? Are empty inbox and filtered-empty work distinguishable from health?
- **CLI:** Do usage errors precede auth/profile resolution? Is every nonstreaming
  JSON result one envelope? Are unknown cursors and partial pages visible? Do
  read commands remain side-effect-free? Is report provenance server-bound?

## Evidence and handoff

Record repository/head and dirtiness, UTC time, exact commands, exit status,
binary hashes, assertion results and limitations. For real reads, add canonical
source identity, reader revision, observation time and coverage. For channels,
record redacted origin identity and actual response/delivery evidence. Keep
synthetic data labeled synthetic. Do not publish raw customer work, personal
conversations, credentials or private logs. A passing local report is not CI,
deployment or a verified complete product.
