# Agent Nexus v0.12.0

This release adds explicit participation for agents you already run, task-scoped
activity views, and versioned participant and PM skill packs. Agent execution
stays on user-owned runtimes.

## Included

- Register arbitrary-provider sessions through the authenticated API, CLI, or
  standalone MCP interface. Stable agent identity, native conversation identity,
  and execution attempts remain separate.
- Record concurrent, nonlocking task participation with retry-safe sequence
  fencing and expiring activity. Participation preserves task assignment, phase,
  source authority, and completion.
- Inspect task participation and bounded agent-detail coverage without exposing
  native session IDs or unrelated private context. Failed and stale reads remain
  visible rather than keeping activity falsely current.
- Configure and verify versioned participant/PM skill content at an explicit
  local path. Owned clean content can refresh; edited or unmanaged content is
  preserved for review. Release archives contain the canonical sources, catalog,
  and agentctl-compatible pack manifests.
- Use optional agentctl identity evidence while keeping explicit identity
  overrides and the generic registration path. Ambiguous inherited context
  requires an explicit identity instead of attributing a parent conversation.

## Compatibility and upgrade

The OSS core, CLI, web UI, and bridge version together as v0.12.0. The companion
hosted SaaS v0.12.0 release must pin this OSS release's exact commit. Agentctl is independently versioned and optional. The minimum for the optional
`agentctl.identity.v1` integration is v0.12.0. Identity and schema-v1 skill-pack
compatibility were tested against that release
([`7b2644a`](https://github.com/Git-on-my-level/agentctl/commit/7b2644ae8124ab5affbe7134eaaf45a0ad8e7dee));
this is not a claim that every later provider version or native session has been
qualified.

The workspace migrates from schema 41 to 42 with additive session and task
participation tables. Take a normal workspace backup before upgrading and retain
the previous deployment artifacts. A downgrade or restore needs its own validated
procedure; checkout restoration alone is not a transactional deployment rollback.

For hosted deployment:

1. Verify the published CLI archive against `checksums.txt` and resolve the OSS
   v0.12.0 tag to its exact commit.
2. Verify `ghcr.io/git-on-my-level/anx-core:sha-<first-seven-commit-characters>`
   exists for that commit, and record its immutable digest/revision. The semantic
   image alias is `:0.12.0`, without the Git tag's leading `v`.
3. Use the matching SaaS release and OSS gitlink. Its updater must stop if the
   desired exact image cannot be pulled; retaining an older image is not a
   successful upgrade.
4. The operator performs cloud deployment. Then check serving versions, health,
   task/source preservation, auth denials, and an authorized synthetic
   participation/replay cycle before treating rollout as verified.

Publishing these artifacts does not deploy the cloud.

## Remaining work

- Automatic consent-scoped project/repository/history discovery and source-tool
  verification, including coverage and freshness evidence
- Existing-PM session attachment, recipient-scoped private conversations, and
  requester-scoped context reads; the legacy optional runner is not proof of an
  existing-agent connection
- Real native-harness skill loading, activation, and automatic supported-harness
  setup; installed bytes and loader compatibility are narrower qualifications
- Verified external push/contact or native resume/history capabilities
- Rich reconciled project summaries and broader real-work dogfooding
